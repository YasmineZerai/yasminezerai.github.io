I built the **five specialized agents** (Order, Complaint, FAQ, Sales, Escalation) of a multi-agent customer support system, our INSAT end-of-year project in a **team of 4**. In the architecture, an agent has to **look before it acts**. My ordered double search stopped the Complaint agent from approving refunds on orders **delivered 46 days earlier**, and all **14 agent test scenarios** pass.

## Problem

In e-commerce support, human agents drown in **200+ policies**, rule-based chatbots break off-script, and a single LLM invents procedures.

## What we built

A **LangGraph orchestrator** routes each request to one of **5 specialized agents**. With **ports and adapters**, the agents never know where data lives, and a separate RAG service runs on **Pinecone** with semantic chunking.

## My part: the agents

I built the shared base loop, then the five agents on top of it. Each agent declares only its system prompt, its tools and its maximum number of tool calls.

<Diagram id="pfa-agent-loop" />

## The decisions that matter

<Decision title="Look before you act, enforced by the architecture">
I made the base loop refuse to run an action tool (refund, cancel, return, ticket, assign) in the same turn as a read tool. The agent has to look first, and **the architecture enforces it, not the prompt**.
</Decision>

<Decision title="Check eligibility before reading the refund procedure">
In early tests with a single search, the Complaint agent **approved refunds on orders delivered 46 days earlier**: it read the refund procedure first. I split it into **two ordered RAG searches**: eligibility first, resolution only once eligibility is confirmed. That removed the behaviour.
</Decision>

<Diagram id="pfa-double-search" />

<Decision title="No answer without a confident source">
Below a **0.6 retrieval confidence**, the FAQ agent rewrites its query and retries. If that fails too, it creates a ticket instead of answering.
</Decision>

### Each agent's rules

- **Complaint**, the only agent allowed to refund: auto-approves under a threshold, escalates above it, refuses outside the 30-day window, applies the EU/UK final-sale exception, **escalates silently to Trust & Safety** on fraud signals, and asks the customer when an item's condition is unverified.
- **Order:** checks ownership before any action, asks for confirmation before cancelling, hands non-cancellable orders to Complaint, and helps customers who forgot their order ID find it.
- **FAQ:** read-only. Spots disguised actions ("can I return my order?") and hands them to Complaint.
- **Sales:** searches and reads purchase history in parallel, checks stock on every candidate, then writes an audit ticket. **A SKU that doesn't exist is blocked before it's recommended.**
- **Escalation:** a fixed 3-step sequence (summarize and set priority, create the ticket, assign a human), so **a human never receives an empty ticket**.

### The rest of the system (team work)

The orchestrator handles intent discovery, slot filling, multi-intent requests, routing and combining answers. Data sits behind the same interface as an in-memory mock or PostgreSQL + MongoDB, and LLMs are served through Replicate. We generated synthetic company documents with **deliberate, controlled conflicts** between them, to test the agents against realistic policy contradictions. The team also built an admin dashboard and an embeddable chat widget.
